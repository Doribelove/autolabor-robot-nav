一、模式1定义

本项目里“模式1”指：

  ./scripts/bringup.sh gps

也就是 GPS 直接提供定位，FAST_LIO 不再发布 odom/TF，只负责 Livox 点云配准并给导航提供 /scan。

模式1主链路：

  CAN 底盘
    -> /odom, /cmd_vel 执行

  GPS
    -> /gps/fix
    -> /gps/heading
    -> gps_localization_node.py
    -> /gps/pose, /gps/odom
    -> TF: camera_init -> base_link

  Livox MID360 + FAST_LIO 点云配准
    -> /cloud_registered_body
    -> pointcloud_self_filter / pointcloud_to_laserscan
    -> /scan

  GPS 目标
    -> /gps/goal_fix
    -> gps_goal_node.py
    -> /move_base_simple/goal
    -> move_base + TEB
    -> /cmd_vel
    -> m2_driver

二、推荐启动方式

终端 1，启动整套 GPS 定位导航：

  cd /home/robot/robot_ws
  source /opt/ros/noetic/setup.bash
  source /home/robot/robot_ws/devel/setup.bash
  TERMINAL_MODE=split ./scripts/bringup.sh gps

当前 GPS 模式默认使用双天线 GNSS 航向：

  GPS_HEADING_SOURCE=dual_antenna

位置来自主 GNSS 的 GGA 经纬度，航向来自 #UNIHEADINGA。双天线航向静止时也能给车头方向，适合室外 GPS 导航。

如果现场临时没有双天线航向，才需要退回旧的单天线/指南针方式：

  GPS_HEADING_SOURCE=auto GPS_COMPASS_HEADING_DEG=45 TERMINAL_MODE=split ./scripts/bringup.sh gps

指南针角度约定：

  0   = 北
  90  = 东
  180 = 南
  270 = 西

脚本内部换算：

  ROS yaw = 90度 - 指南针角度

如果直接传 ROS 弧度值，仍然支持：

  GPS_INITIAL_YAW=1.5708 TERMINAL_MODE=split ./scripts/bringup.sh gps

注意：GPS_INITIAL_YAW 优先级高于 GPS_COMPASS_HEADING / GPS_COMPASS_HEADING_DEG。

调试指南针换算但不启动无人车：

  GPS_COMPASS_HEADING="东北45度" ./scripts/bringup.sh --print-gps-yaw

终端 2，如果要接 RabbitMQ 的 GPS 目标：

  cd /home/robot/robot_ws
  source /opt/ros/noetic/setup.bash
  source /home/robot/robot_ws/devel/setup.bash
  ./scripts/rabbitmq_gps_goal_bridge.py

终端 2，如果要运行 GPS 电子围栏和避障测试菜单：

  cd /home/robot/robot_ws
  source /opt/ros/noetic/setup.bash
  source /home/robot/robot_ws/devel/setup.bash
  ./scripts/gps_test_tasks.py

测试菜单数字含义：

  1：发布当前车头正前方 8m 的 GPS 目标。
  2：以当前位置和当前车头方向为基准，保存前后左右 10m 的永久矩形电子围栏。
  3：在当前位置前后左右 10m 范围内随机发布 GPS 目标，用于阻拦测试避障。
  4：显示当前电子围栏。
  5：清除永久电子围栏。

电子围栏文件固定保存到：

  /home/robot/robot_ws/config/gps_test_fence.json

注意：电子围栏只在 scripts/gps_test_tasks.py 运行时生效。只正常启动 ./scripts/bringup.sh gps 时，不会受这个测试围栏约束。

GPS 测试任务 1 的关键逻辑：

  - scripts/gps_test_tasks.py 使用 /gps/odom 的当前位置和 yaw 计算车头正前方 8m 的 GPS 点。
  - gps_goal_node.py 把 /gps/goal_fix 转成 /move_base_simple/goal。
  - 当前目标姿态默认 goal_yaw_mode=bearing，即使用当前位置指向目标点的方向，不再固定 yaw=0。

如果任务 1 仍然调头或明显不是正前方，优先查：

  rostopic echo /move_base_simple/goal
  rostopic echo /gps/odom
  rostopic echo /gps/heading
  rosparam get /gps_goal/goal_yaw_mode
  rosparam get /gps_goal/odom_topic

判断标准：测试脚本打印的目标 x/y 应和 /move_base_simple/goal 基本一致；如果目标点已经在真实车头后方，说明 /gps/odom yaw 或双天线安装方向需要校正。

RViz 手动发送目标时：

  - Fixed Frame 必须使用 camera_init。
  - RViz 的 2D Nav Goal 应发布到 /move_base_simple/goal，消息里的 header.frame_id 应是 camera_init。
  - gps_goal_node.py 和 scripts/gps_test_tasks.py 都不再 latch 发布目标，避免旧 GPS 目标在节点重连时覆盖 RViz 目标。
  - 如果 RViz 目标点突然变化，先查 /move_base_simple/goal 当前有哪些 publisher：

    rostopic info /move_base_simple/goal
    rostopic echo /move_base_simple/goal

无障碍前方目标仍绕弯时，重点检查 TEB 与 M2 驱动的 /cmd_vel 语义：

  - m2_driver 订阅 /cmd_vel 时，把 angular.z 当角速度，再换算成前轮转角。
  - TEB 必须设置 cmd_angle_instead_rotvel=False，不能把 angular.z 直接当 steering angle。
  - 当前 dingo/nomap TEB 已按“直线优先但保留避障机动性”调参：
    max_vel_theta=1.5
    acc_lim_theta=0.5
    min_turning_radius=1.2
    global_plan_viapoint_sep=0.8
    weight_shortest_path=4.0
    weight_viapoint=8.0
    enable_homotopy_class_planning=True
    costmap_obstacles_behind_robot_dist=0.8

现场确认：

  rosparam get /move_base/TebLocalPlannerROS/cmd_angle_instead_rotvel
  rosparam get /move_base/TebLocalPlannerROS/max_vel_theta
  rosparam get /move_base/TebLocalPlannerROS/acc_lim_theta

四、我实际运行模式1时的发现

我已经在真实无人车上实际启动过模式1，并做过 ROS 参数、topic、TF、odom 方向的核查。

当时发现的关键问题：

1. 模式1虽然叫 GPS 定位，但之前默认仍有 use_wheel_odom=true 的风险。

   这会把底盘 /odom 和 GPS ENU 坐标混在一起。如果底盘里程计坐标系和 GPS 坐标系没有对齐，/gps/odom 会被带偏，表现为车认为自己的姿态/位置和真实 GPS 不一致，导航时可能乱跑。

   当前已修正：

     scripts/bringup.sh
       GPS_USE_WHEEL_ODOM=false

   GPS 模式默认不再融合底盘 /odom，只使用 GPS 位置直接形成 /gps/odom。

2. 底盘 odom 的 child_frame_id 曾经不适合导航检查。

   当前已修正：

     src/autolabor_core/autolabor_canbus_driver/autolabor_canbus_driver/launch/drive_only.launch

   把 is_odom_child_baselink 改成 true。

   我运行后验证过：

     /odom child_frame_id = base_link

3. TEB 参数里 penalty_epsilon 之前和 max_vel_x=0.1 有冲突风险。

   之前 GPS 模式 max_vel_x=0.1，同时 penalty_epsilon=0.1，TEB 会有不合理警告，速度约束边界太紧。

   当前已修正：

     GPS_TEB_PENALTY_EPSILON=0.03

   并传入：

     robot_bringup navigation_arena.launch
     real_nav_nomap.launch
     move_base_teb_nomap.launch

   我运行后验证过：GPS 模式下没有再出现之前那个 TEB max_vel_x / penalty_epsilon 警告。

4. 当前模式1已改为双天线 GNSS 航向。

   位置来自主 GNSS 的 GGA 经纬度，航向来自 #UNIHEADINGA。双天线能在静止时提供车头方向，不再依赖单天线 GPS course 或运动差分推航向。

   当前默认：

     GPS_HEADING_SOURCE=dual_antenna
     GPS_HEADING_REQUIRED_SOLUTION_STATUS=SOL_COMPUTED
     GPS_HEADING_REQUIRED_POSITION_TYPES=NARROW_INT
     GPS_ANTENNA_OFFSET_X=-0.3
     GPS_ANTENNA_OFFSET_Y=0.0
     GPS_HEADING_MIN_SPEED=0.05
     GPS_MIN_COURSE_DISTANCE=0.2

   gps_localization_node.py 会把主天线位置按 base_link 内的安装偏移换算到底盘中心：

     base_position = antenna_position - R(yaw) * antenna_offset

   因为当前主天线在 x=-0.3m，发布给导航的 base_link 位置会在主天线前方 0.3m。

   如果双天线航向消息超时或质量不满足要求，GPS 模式会保持最近一次可用 yaw，不会在默认配置下退回低速不稳定的 GPS course。

5. 激光雷达点云不是“挂载在 GPS 点上”。

   模式1里 GPS 发布 camera_init -> base_link，确定车体在全局局部坐标 camera_init 下的位置和朝向。

   Livox/FAST_LIO 只提供点云配准结果，点云经过固定/动态 TF 转换到 base_link/camera_init 相关坐标下，再投影成 /scan 供 costmap 避障使用。

   导航看到的是：

     定位：/gps/odom
     障碍物：/scan

   不是把每一帧点云绑定到某个 GPS 点上，而是通过同一套 TF 坐标树把定位和障碍物放进同一个导航坐标系。

八、模式1乱跑的主要风险点

如果车在模式1乱跑，优先怀疑以下几类：

1. 双天线航向没有进入导航

   当前 GPS 模式应由 #UNIHEADINGA 提供车头方向。若 /gps/heading 不发布、质量不满足要求、或 heading 超时，camera_init -> base_link 的 yaw 会保持最近一次有效值，导航方向可能不对。

   检查：

   - rostopic echo /gps/heading
   - rosparam get /gps_localization/heading_source
   - rosparam get /gps_localization/heading_required_solution_status
   - rosparam get /gps_localization/heading_required_position_types

2. 双天线安装方向和 base_link 前向不一致

   #UNIHEADINGA 的 heading 表示双天线基线方向。这个方向必须和车辆定义的前向一致；如果主副天线前后装反或横向安装，TF yaw 会稳定但整体偏 90 度或 180 度。

   建议：

   - 静止时观察 /gps/heading，并和车头真实指南针方向对比。
   - 小距离前进 1-2 米，确认 /gps/odom yaw 和车头方向一致。
   - 如果稳定偏固定角度，需要增加双天线安装 yaw offset，而不是改目标点。

3. GPS position 抖动或跳点

   位置仍来自主 GNSS GGA。双天线解决的是车头 yaw，不解决经纬度跳点。

   当前已设置：

   - stationary_hold_radius=0.8
   - position_filter_alpha=0.25
   - max_fix_jump=5.0

   如果现场 GPS 抖动仍大，可以继续调这些位置滤波参数。

4. /gps/odom 和 /scan 坐标关系错

   导航必须同时满足：

   - /gps/odom frame_id 是 camera_init
   - /gps/odom child_frame_id 是 base_link
   - /gps/odom 位置已经从主天线补偿到底盘中心
   - camera_init -> base_link TF 可用
   - /scan 能被 costmap 正确接收

5. GPS 目标点或 RabbitMQ 消息错误

   检查：

   rostopic echo /gps/goal_fix
   rostopic echo /move_base_simple/goal

   如果目标点转换后的局部坐标方向明显反，检查：

   - GPS origin 是否和定位节点一致
   - 纬度经度字段是否反了
   - RabbitMQ JSON 里的 LAT/LON 是否正确
