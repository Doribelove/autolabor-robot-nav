## 失败链路的原始证据

### 1. Hybrid A* 初始搜索和整段重算均成功

第二次转场先得到：

```text
coverage planned direct Hybrid connector:
3.90m, parts=3, final=yes, expansions=19563,
cost=13.47s, reverse=0.90m, switches=2
```

首个 cusp 的实测接回弦角为 12.7°，超过 5.7° 门限后，系统按当前设计从实测位姿到
原最终清扫入口重算，而不是只规划到下一个 cusp。该次搜索也成功：

```text
coverage planned direct Hybrid connector:
3.30m, parts=2, final=yes, expansions=1070,
cost=10.46s, reverse=1.20m, switches=1
```

因此不能把该阶段称为“Hybrid A* 算不出路径”。

### 2. TEB 固定倒车 action 是第一个执行故障点

`hybrid_teb_command_mux` 已正确装载 `gear=reverse`，在线 TEB 参数也确认为
`motion_direction_mode=-1`、`max_vel_x_backwards=0.30`、最小转弯半径 1.35 m。但在
03:17:01--03:17:05 之间，`move_base` 连续记录：

```text
TebLocalPlannerROS: optimized command violated the fixed-gear contract.
Resetting planner...
```

源代码在速度饱和前检查 TEB 原始纵向速度符号；正向候选不会被传给底盘，而是被置零并
清除当前优化带。因此安全门工作正确，但造成 R 段反复重置/停车。随后管理器连续 3 个
样本测到路径横向偏差 0.351 m（刚超过 0.35 m 门限，航向偏差仅 5.6°），取消当前精确
action generation 并从实时位姿到最终入口重规划。这个事件触发动作本身符合设计。

当前日志只能证明 TEB 软优化最终给出了错误符号，尚不能仅凭日志把内部诱因唯一归结为
障碍代价、终点姿态还是优化权重。新空旷区域对照将用于区分静态边界是否为主要诱因；
在修复前仍应保留固定档位硬门，不能为了让车辆继续运动而放行反号命令。

### 3. 异常恢复不是搜索失败，而是候选被策略拒绝

进入入口附近恢复后，Hybrid 每次返回同一条 2.10 m 候选：前进 1.80 m、倒车 0.30 m。
`coverage_manager.py` 对入口恢复设置总长不超过 4.00 m且累计前进不超过 1.20 m，以阻止
车辆大幅前进绕圈。该候选总长合格，但前进长度超限 0.60 m，于是在 Hybrid service 成功
返回后被管理器拒绝：

```text
entry-alignment Hybrid path was rejected as a forward detour:
total 2.10m, forward 1.80m, reverse 0.30m
```

原始状态文字把这一结果概括成 `no feasible detour`，容易误诊为 Hybrid 搜索失败。准确
含义应是“存在几何路径，但没有通过当前入口恢复策略的候选”。操作员两次人工恢复后，
起点/目标和规则未变化，均重复相同拒绝并再次暂停；继续点击恢复没有收益。

### 4. 次要现象

- `/scan` observation buffer 在多个 action 交接/规划窗口出现 0.39--2.09 s 不新鲜告警；
  本轮所有初始 Hybrid 与重算搜索仍成功，日志没有把最终暂停归因于碰撞或全局路径安全
  许可失效，因此它不是已证实的终止根因，但后续实验需继续统计。
- 第一轮已完成的线 1 -> 线 2 转场中，每个 cusp 都因接回弦角超限而重算。正常 cusp 没有
  被状态机直接当作异常，但实测交接精度使“缓存后缀复用”完全没有发生，造成 34.716 s
  的转场和 5 次路径生成，远慢于仿真结果，属于独立的效率问题。
- mux 的 `stale TF/TEB/path lease or unsafe planner permit` 告警主要出现在 action 交接及
  TEB 被固定档位门重置之后；它解释零速保持，不是 Hybrid 搜索返回失败的证据。
