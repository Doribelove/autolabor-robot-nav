# 2026-08-31 导航实验问题清单

本文记录 2026-08-31 实机实验已经确认的现象、证据、当前判断和后续验证顺序。目的
是避免把不同阶段的问题混在一起，也避免在没有对照实验时继续叠加参数修改。

## 本轮先修复的问题：TEB 速度里程计映射错误

静态地图模式下存在两套含义不同的里程计：

- `/Odometry` 是 FAST-LIO 位姿和 TF 链的数据源，但它的 twist 始终为零；
- `/odom` 是 M2 底盘的轮速反馈，包含 TEB 需要的实际线速度和角速度。

源码已经把 `TebLocalPlannerROS/odom_topic` 参数设置为 `/odom`，但同一个 move_base
节点还有一条 `odom -> /Odometry` 的 ROS remap。ROS 名字解析时，这条 remap 会继续
作用到参数中写成绝对名字的 `/odom`，所以运行中的 `/move_base` 实际只订阅了
`/Odometry`。这就是“参数服务器看起来正确，节点实际订阅仍然错误”的原因。

实验中同一时刻可见 M2 `/odom` 速度约为 `-0.353 m/s`，而 FAST-LIO
`/Odometry` 的 twist 为 `0.000 m/s`；TEB 优化轨迹的起始速度也为零。与此同时，TEB
未来轨迹速度能够达到约 `1.51 m/s`，说明 Qt 下发的速度上限和 TEB 时间优化目标已经
生效，速度反馈错误才是每个优化周期都从“车辆静止”开始计算的直接原因。

修复方式是让 move_base 的 `odom` remap 与 TEB 参数统一使用 `teb_odom_topic`：静态
地图模式实际订阅 `/odom`；无图 FAST-LIO 模式仍使用 `/Odometry`；GPS 模式仍使用
`/gps/odom`。FAST-LIO 的全局位姿和 TF 链没有改变。

该项在下一轮实验前必须完成三层验收：源码合约测试、J6M 安装版本检查、运行中的
`rosnode info /move_base` 实际订阅检查。只有实际订阅显示 `/odom` 才算修复生效。

## 剩余问题一：普通点到点导航会长时间卡住

状态：已确认现象；修复 `/odom` 后需要先复验，暂不继续改参数。

最后一次普通点到点目标总耗时约 `218.25 s`，其中约 `138.16 s` 处于几乎没有进展的
状态。该阶段的主要证据是：

- 全局剩余路径长期保持约 `27.45 m`；
- 导航指令线速度平均约 `0.028 m/s`，轮速里程计平均约 `0.002 m/s`；
- 前轮角度长期接近 `28.3°`；
- 前方扫描最近有效距离约 `1.69 m`，不是传感器完全缺流；
- TEB 多次报告预测足迹在第 15 个检查位姿命中致命格，坐标约为
  `(19.174, -25.296)`，随后重置轨迹。

当前形成了“轨迹不可行 -> TEB 重置 -> 输出极小速度 -> 底盘几乎不产生位移 -> 再次
规划同类轨迹”的循环。`/odom` 修复能够让 TEB 正确知道车辆已经在运动，但车辆真正停住
时正确反馈仍然是零，因此不能假定它会单独解决这一类致命代价格附近的卡死。

普通 move_base 当前关闭了 Ackermann 不安全的原地旋转恢复，同时
`oscillation_timeout=0`，所以没有一个经过实车验证的“长期无进展”退出或换拓扑机制。
后续若复现，优先设计 Ackermann 可执行的有限恢复或任务层无进展处理，不能恢复原地旋转，
也不能用强制最小速度穿过致命格。

## 剩余问题二：覆盖任务在线间转场第 5/10 段暂停

状态：已确认现象；属于 Hybrid 全局连接与 TEB 可跟踪性之间的接口问题。

本次覆盖任务已经完成前面的 Navfn 入场、扫掠和一段 Hybrid 转场，但在第 `5/10` 段
线间转场中，初始尝试和三次重试均在 `8 s` 内位移不足 `0.10 m`。每次失败后等待
`10 s`，最终按现有安全策略进入人工暂停，而不是跳过依赖的下一条清扫线。

这说明“Hybrid 能生成无静态碰撞的运动学路径”不等于“TEB 在当前实时代价图、当前
车身姿态和入口空间下能够跟踪”。重试期间主要复用了同一类缓存连接，也没有形成明确
不同的可行拓扑。后续需要记录每个换向子段的档位、起终姿态、缓存路径、TEB 局部轨迹和
致命格位置，再判断是入口空间不足、缓存续接、档位交接还是局部可行性问题。不能仅通过
降低障碍代价或允许未知区来让任务通过。

## 剩余问题三：控制和代价图线程存在明显超期

状态：已确认负载现象；尚未证明它是每次卡死的唯一原因。

本次日志去重统计中，move_base 控制循环和局部代价图更新存在大量错过周期告警，部分
周期达到约 `200–350 ms`，而控制目标周期是 `100 ms`。当前静态配置同时包含：

- `20 m × 20 m`、`0.10 m` 分辨率的滚动局部代价图；
- TEB 最多检查 50 个轨迹位姿；
- 较多实时障碍点和同伦候选；
- 每周期多轮外层、内层图优化。

下一轮要同步记录 CPU、控制循环间隔、代价图更新时间、TEB 候选数和轨迹点数。若在
空旷区域也持续超期，再针对计算量做 A/B；不能为了降负载而弱化完整 footprint、未知区
或致命障碍的硬约束。

## 剩余问题四：部分普通目标使用了错误坐标系

状态：已确认一次独立输入错误。

日志中有一次普通目标使用 `camera_init` 坐标系，而静态地图导航规划器要求 `map`，该目标
被正确拒绝。Qt 相对目标或 AI 入口必须先通过当前新鲜 TF 转换到 `map`，再提交给
move_base。这与 TEB 卡死不是同一个问题，后续应单独补入口合约和回归测试。

## 剩余问题五：前轮大角度和左右摆动仍需拆分判断

状态：现象明确，机械控制根因尚未确认。

实验中前轮多次接近机械角度边界，并出现方向反复变化；TEB 同时报告轨迹不可行和振荡。
现有证据既可能对应局部规划在障碍边缘反复换解，也可能叠加前轮执行超调。静止时前轮
反馈基本稳定，不能据此证明运动中没有超调。后续必须同时间轴对比 TEB 输出曲率、
`/cmd_vel`、前轮目标角、前轮反馈角和车体航向误差，再决定修改规划敏感度还是底盘控制。

## 剩余问题六：实验结束后的定位退化/丢失

状态：发生在导航目标成功、导航指令已经为零之后，暂不归因于导航算法。

实验末尾定位从 `LOCALIZED` 变为 `DEGRADED/LOST` 时，move_base 目标已经成功且导航
输出为零，但轮速里程计仍出现非零运动。该阶段可能包含人工或外部运动，和前面的导航
卡死不应混为一个根因。下一轮若没有人工接管仍复现，再单独检查 ICP 重叠率、点云遮挡、
时间同步和 `map -> camera_init` 更新。

## 已排除或暂不改动的项目

- Qt 规划参数确实已经动态下发：本次状态显示最大前进速度约 `1.30 m/s`，TEB 未来轨迹
  也能生成高于该量级的速度轮廓；“界面完全没有生效”与现有证据不符。
- `/scan`、前后 LD19 参与状态和局部代价图在主要导航阶段都有新鲜数据，不能把本轮所有
  问题归为雷达断流。
- 未知区、地图外、静态致命格和完整 footprint 继续是硬障碍，本轮不放宽。
- 不启用 Ackermann 车辆无法安全执行的原地旋转 recovery。

## 下一轮实验顺序

1. 冷启动并由操作员重新给出真实初始位姿，等待定位为 `LOCALIZED`。
2. 只读确认 `/move_base` 实际订阅 `/odom`，且不再订阅 `/Odometry` 作为 TEB 速度源。
3. 先在空旷区域以不高于 `0.3 m/s` 做一条普通点到点，对比 `/odom` 修复前后的起步、
   巡航速度、停止次数、TEB 起始速度和控制周期。
4. 再做同一区域的覆盖任务，重点观察首线 Navfn 入场和第一个 Hybrid 换向转场。
5. 若仍卡住，保持现场不人工推动片刻，截取同一时间窗内的全局路径、局部轨迹、代价图、
   轮速和前轮角；随后由操作员决定取消或接管。
