三、官方六相机模型基线（已实测）

固定 Hugging Face revision：1aada6677d1686efca1281a83b137c4592c267fe。
HBM 本地路径：runtime/bev_feature_20261101/official/nash_m/compile/model.hbm
大小 75298080 字节；SHA256：
05443372d993714db0b226de6771a114876217fb02248c7bb1ec077a8b1af2e6
浮点权重、README、LICENSE/各语言版本、NOTICE 同目录保存，下载清单包含哈希。
官方浮点 checkpoint 共 877 个 state_dict tensor；仅检查键和形状，没有把其
HEAL 模块键强行载入 torchvision 原型。文件没有被称为垃圾训练权重。

hrt_model_exec model_info 真实加载成功：bev_vtv2_resnet50_nuscenes。
输入共 14 个：6 对 NV12 Y/UV（256x704 Y，128x352x2 UV），
points0/points1 均为 (10,128,128,2) S16，scale 分别为 0.0078125、0.03125。
输出共 6 个 SCALE S32，通道依次为 2、1、3、2、2、10，空间 128x128。
这是六相机交通目标 ABI，不能拿四路图片填进去就称为四路垃圾模型。

受控基线：neutral NV12 + 零采样索引，single core / single thread / 100 frames。
平均模型调用延迟 16.6277 ms；BPU inference 16.5421 ms；59.8973 FPS。
profile 记录一个 BPU 子图，CPU inference time 0；BPU core process 16.3745 ms。
这证明该官方 HBM 的实际推理在 BPU；CPU 的文件/内存/提交工作仍然存在。
没有逐层编译报告，不能把单个子图拆成编码器/融合/检测头各自延迟。
这些输入仅用于执行与性能检查，未验证交通目标检测精度，亦不是本车垃圾性能。

常驻接口另测：复用 tensor_executor.cpp 的模型加载、cached 内存、stride 拷贝、
cache flush、hbDNNInferV2、hbUCPSubmitTask、等待及输出反量化。
新增 S16 SCALE 输入和实际 scale/zero-point 元信息；Python 类型绑定接受 int16。
12 次相同输入（前 2 次预热），后 10 次 vendor 调用均值 16.8578 ms，
六个输出均有限值、重复输入最大差为 0。新垃圾 HBM 的真实 ABI 尚不存在，未绑定它。
板端 native_reference 是常驻 session 的验证程序，不是在线垃圾推理 ROS 节点。
编译使用既有只读 Ubuntu sysroot；共享库依赖由板端 Debian 运行库解析，实际加载已通过。

测试短暂停止持有旧 BPU 独占锁的 j6m-b-camera-receiver.service，随后恢复 active；
全过程沿用 preview_worker.lock。四格相机与像素 BEV 源服务保持 active。
第一次无输入文件的 exploratory perf 仅留证，正式数字取 official_hbm_perf_valid.log。

五、已实现的四路浮点原型与 HEAL 待接部分

路径：src/application/autolabor_fod_vision/src/autolabor_fod_vision/bev_feature/
model.py：共享 ResNet50/FPN -> depth/context -> 两次 GridSample -> Mul ->
四视角/高度采样求和 -> 单一 BEV 特征图 -> 小型 BEV encoder -> trash 热图和 x/y offset。
这是实际特征融合，未采用四路独立检测框拼接；融合操作在模型图内。
geometry.py：CPU 根据本车 K/位姿、显式 rig/base 平面变换生成采样网格和 valid。
网格暂定 x[-2,4]、y[-3,3]m，5cm/cell，120x120；约10cm目标占两格只是设计起点，
更小垃圾的最小尺寸未确认，分辨率需随实测召回率/BPU资源调整。
row 增加沿 +X，column 增加沿 +Y；offset 的顺序为 x/y，范围[0,1)。
全局 BEV 峰值解码与米制 NMS，默认半径12cm；距离更近的不同垃圾可能被误合并，需标注验收。
data.py：同步/时钟/坐标/图像/唯一实例校验，热图及格内偏移监督。

该原型不等同于 HEAL 0.0.2 移植：
- 未载入官方 checkpoint；当前结构验证用随机权重。
- 使用四个地面附近高度假设，尚未移植官方 distance-topk 视锥采样。
- 原型 BEV encoder 是小型卷积模块，尚未复用官方 ResNet50/FPN BEV encoder。
- 未完成官方量化模块替换、qint8/qint16 配置、QAT/PTQ 和 nash-m 编译。
官方 GridSample 分开处理 depth/feature 的参考依据：
https://developer.horizon.auto/blog/14085
取得源码后必须按实际源码改 num_views=4、数据相机顺序、视锥索引、预处理和输入导出，
保留官方 backbone/FPN/LSS/BEV encoder，检测头改为单类 heatmap+xy-offset；
不能只把模型卡里的6改成4或复用 nuScenes 的 points0/points1。

已实测：Jetson CUDA 原型 shape/fusion smoke 平均42.32ms（3次测量、2次预热），
输出(1,1,120,120)/(1,2,120,120)；仅作本机原型执行指标，不是BPU或端到端性能。
真实四路快照完整图反向传播均有非零梯度，ONNX checker通过；导出图包含
GridSample/Mul/ReduceSum/Conv。文件名 UNTRAINED_graph_smoke.onnx，不能作为已训练模型部署。
训练、训练后推理和正式导出 CLI 已实现，但没有真实米制训练数据，未执行正式训练。

六、ROS 接入及验证边界

fod_bev_observations_node.py 订阅 /fod/bev/decoded（String JSON，明确的新模型适配边界）：
  stamp_ns、source_stamps_ns{front,left,right,rear}、clock_domain=ros_epoch_ns、
  clock_verified=true、frame_id、position_std_m、centers[{x,y,confidence}]、model_bpu_ms。
采集参考时刻取四路最新时刻，限制组内20ms偏差；不使用发送/接收时刻冒充采集。
position_std_m 是待残差验证的观测噪声参数；合成测试中 .05 不是实测精度承诺。
模型输出若是 rig 坐标，必须有该时刻 source->base TF；输入本身已是 base 则直接使用。
map 转换用采集时刻 map<-base TF，缺失时不退回 Time(0)/最新 TF。

复用 autolabor_fod_msgs/FodGroundObservationArray：
  /fod/bev/ground_observations（base_link，米）
  /fod/bev/map_observations（map，米）
复用 autolabor_fod_vision/tracking.py 的 MultiTargetTracker，map 中关联：
  /fod/bev/markers（MarkerArray，稳定ID，RViz）
  /fod/bev/latency（模型BPU耗时、capture到map发布耗时）
仅做观测/地图显示，不接原自动清扫控制；新 HBM producer 仍待模型完成。

ROS Noetic 私有 master 11591 上，实际 roslaunch + rosbag --clock 回放通过：
20条合成四路时间/解码中心+移动转向TF，固定地图点(2,1)m稳定，始终1个跟踪ID，
未重复标点；算术误差约6.28e-16m，只证明坐标实现，绝不是实车定位精度。
无效时钟、超skew、缺TF、重复旧帧均未产生地图观测。
回放的约数十毫秒为模拟ROS时钟差，不能作为真实采集到发布延迟。
本轮真实交界处去重、车换位置地图稳定性、对实测点定位误差均未验收；
四路垃圾 BPU 延迟、真实端到端延迟均暂无数字。
评价工具 evaluate.py 将重复点、误差、静止点抖动、跟踪ID及两类延迟分开统计。
